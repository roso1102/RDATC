# Live pipeline measurements — 31 October 2026

Tool: `python -m ares.measure` (`ground_station/ares/measure.py`), polling the live backend
`/api/state` at 10 Hz. Raw samples and summaries are saved in `benchmarks/pipeline/`.
Setup: port 8000 backend, camera `http://ares.local/capture` (firmware `ares-node-0.2`), radar BLE
streaming, laptop YOLOX-Nano detector, provisional fusion, clear profile. No person was in view for
most of the baseline run.

**Single-owner acquisition:** the backend fetched 60 frames while 4 clients read 2,299. The node's
`frames_served` rose by 120; process inspection showed a Chrome network process also connected
directly to the node (its own auto-refreshing viewer page). The extra node requests came from that
browser, not from the backend or the preview clients.

## Run 2 — node hard reset at 20 s (90 s)

File: `2026-10-31T001820-node-reset.json`. The ESP32 was hard-reset over USB with esptool
(USB power maintained; this is a reboot, not a power or Wi-Fi-only loss).

| Measure | Result |
|---|---|
| Reboot detected | yes (node uptime 968,456 ms → 9,670 ms) |
| Camera unavailable to the operator | **10.2 s** (STALE then ERROR, then READY), recovered automatically |
| Node boot to first served frame | ~9.7 s (node uptime of the first frame after reboot) |
| Overall camera rate / availability | 0.82 fps, 88.7% of polls (includes the outage) |
| Receive age | p95 1,078 ms (max 2,953 ms around the outage) |
| Detection coverage | 100% of received frames |
| Fusion | continued at 1.95 Hz; during the outage the decision read `NO_PERSON_INDICATED_PARTIAL_COVERAGE` |
| Radar | 9.69 Hz, unaffected |

The backend's recovery lags the node by up to one failed-request cycle (3 s timeout + 0.75 s
interval). The esptool completion time in this file is mislogged (recorded before the call ran);
fixed in the tool afterwards. The reboot itself is confirmed by the uptime counter.

## Run 3 — camera interval 0.5 s, same baseline (60 s, 4 clients)

File: `2026-10-31T002325-baseline-4clients-0.5s.json`. Backend default `camera_interval_s` changed
from 0.75 s to 0.5 s (now also settable with `ARES_CAMERA_INTERVAL`); backend restarted with radar.

| Measure | 0.75 s (run 1) | 0.5 s (run 3) |
|---|---|---|
| Camera rate | 0.95 fps | **1.22 fps** |
| Receive age p50 / p95 / max | 500 / 969 / 1,250 ms | **391 / 797 / 1,172 ms** |
| Fetch duration p50 / p95 | 250 / 406 ms | 281 / 469 ms |
| Capture-to-receive bound (age p95 + fetch p95) | ≈ 1.4 s | ≈ 1.3 s |
| Detector coverage | 100% | 100% |
| Inference p50 / p95 | 17.6 / 33.8 ms | 19.8 / 64.0 ms |
| Fusion rate | 1.89 Hz | 1.92 Hz |
| Radar rate / age p95 | 9.45 Hz / 109 ms | 9.5 Hz / 109 ms |
| Backend frames vs node `frames_served` delta | 60 vs 120 (browser on node) | 77 vs 79 |
| Camera outages | none | none |

Node fetch time rose slightly and inference p95 roughly doubled (more frequent detection alongside
four preview clients on the same laptop), but both stay well inside the frame budget. Node RSSI
differed between runs (-41 vs -33 dBm), so the node's position is a confounder. One 60 s run each;
not a long-duration result.

each ~0.25-0.3 s fetch. The default is now 0.5 s (run 3).

## Not covered

- Wi-Fi loss without reboot (hotspot off or out of range). The laptop uses the same hotspot, so
  this needs a separate setup.
- Wi-Fi rejoin refusal: an earlier boot showed the hotspot refusing association; if that outlasts
  the firmware's 30 s window the node stays offline until reset (not recovered automatically).
- Long-duration stability (target: up to one hour), radar disconnect/reconnect, and concurrent
  recording load.
- Effect of the intermittent camera D2 wire on these numbers.
