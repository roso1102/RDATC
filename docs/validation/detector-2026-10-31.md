### Colour-bar wiring diagnosis

[Captured test pattern](colorbar-2026-10-31.jpg), mean RGB per bar (JPEG, 8-bit):

| Expected | R | G | B |
|---|---|---|---|
| white | 249 | 124 | 216 |
| yellow | 216 | 124 | 87 |
| cyan | 40 | 99 | 215 |
| green | 7 | 112 | 9 |
| magenta | 232 | 12 | 200 |
| red | 200 | 24 | 1 |
| blue | 25 | 4 | 154 |
| black | 0 | 0 | 0 |

Green never exceeds ~124 where it should be full, while red and blue reach full scale: the green MSB is
missing. In RGB565 the green MSB (G5) is bit 2 of the first byte, carried on camera **D2 → GPIO10**. This
identifies D2 as the faulty line; the other seven data lines carry their bits in the pattern. The test pattern
itself is noise-free, so the speckle in scene frames is sensor/scene-related (light level, gain, focus), not
wiring.

### Recheck after the D2 wire work

Boot log captured over USB after an esptool hard reset: camera init OK (PID 0x76 / VER 0x73), PSRAM 8 MB,
pin check **D2 STUCK LOW**, all other data pins toggling. About a minute later the
[colour bars](colorbar-after-d2-2026-10-31.jpg) measured correctly:

| Expected | R | G | B |
|---|---|---|---|
| white | 247 | 252 | 248 |
| yellow | 216 | 253 | 88 |
| cyan | 39 | 228 | 248 |
| green | 8 | 240 | 7 |
| magenta | 232 | 12 | 232 |
| red | 200 | 24 | 0 |
| blue | 24 | 4 | 153 |
| black | 0 | 0 | 0 |

Green now reaches full scale, so D2 carried data at that moment, and a
[scene frame](scene-after-d2-2026-10-31.jpg) showed natural colour without the magenta cast. Because the
boot check minutes earlier still reported D2 stuck low, treat D2 as **possibly intermittent** until a later
boot check and repeated bar captures agree.

Same boot: the Pixel hotspot first refused association (`Association refused too many times`, reasons
208 then 203), then the node connected on retry (RSSI -50 dBm). Before that reset the node had been off the
network for about 6.5 minutes; a refused association that outlasts the 30-second wait leaves the node
offline until reset, which the current firmware does not recover from by itself.

to disable, `ARES_DETECTOR_THRESHOLD`, `ARES_DETECTOR_PROFILE=laptop|pi5_emulated`.

### Behaviour

- Runs once per new camera frame in a background thread; results carry the source `frame_id`.
- Frames flagged `SENSOR_TEST_PATTERN` are never passed to the detector.
- When the camera is stale/unavailable, the detection is withdrawn (`CAMERA_UNAVAILABLE`).
- `assessment.status` becomes `CAMERA_DETECTION_ONLY` with a person count; `presence_score`
  stays null and `fusion_enabled` false. Radar fusion is not implemented.
- Each result is recorded as a `person_detection` event with model hash, threshold and location.
- The dashboard draws boxes only when the detection's `frame_id` matches the displayed frame.
